# mem0 のアーキテクチャ転換が何をもたらすか

## 要約

mem0 は 2026 年 4 月に、記憶の書き方を大きく変えました。

- **書込み**: 旧方式は 2 段でした。会話から事実を取り出したあと、似た既存の記憶と照らし合わせ、LLM が追加・更新・削除・何もしない（ADD・UPDATE・DELETE・NOOP）を選んでいました。新方式は、1 回の LLM 呼び出しで事実を**追加するだけ**（ADD-only）です。上書きも削除もしません。エージェント自身の発言も、利用者の発言と同じ重みで記憶にします。
- **関係**: OSS 版から外部のグラフ DB（Neo4j など）への対応を外しました。代わりに、ベクトルストアの中に実体（固有名詞など）の索引を持ち、検索の順位を上げる「実体リンク」を入れました。
- **読み出し**: 意味の近さ・キーワード（BM25）・実体の一致の 3 つの信号で採点し、1 つの順位に融合します。5 月には、時間の推論と記憶の減衰を、有償のホスト版（Platform）にだけ足しました。

この転換の中心は、**矛盾の解決を、書込み時の判断から読み出し時の順位へ移したこと**です。

- **得るもの**: 書込みが速く安くなり、履歴が消えなくなります。書込み時に LLM が誤って記憶を消すこともなくなります。
- **失うもの**: 古い事実と新しい事実が並んで残ります。どちらが今の事実かは、検索の順位と、それを受け取るモデルが決めることになります。mem0 自身も、「知識の更新」が加算型の構造でいちばん難しい分類だと認めています。利用者が考えを変えたときの訂正や、消してほしいと言われたときの忘却は、アプリケーションが明示に操作する必要があります。
- **構造の変化**: 型付きの関係（グラフの辺）は、OSS からも Platform の応答からも消えました。時間の扱いは Platform だけにあります。OSS と Platform の差が広がりました。

根拠の大半は mem0 自身の発表です。ベンチマークの数値は mem0 が自社の Platform で測ったもので、ページによって値が食い違い、回答と採点に使ったモデルも書かれていません。この文書では、数値は方向の目安にとどめます。移行文書に書かれた API の変更を、確かな根拠として扱います。

## 変更の内容（時系列・根拠）

旧方式は、2025 年の論文（[arXiv 2504.19413](https://arxiv.org/abs/2504.19413)）が述べる 2 段の書込みです。新方式は、2026 年 4 月の発表と、同じ時期の SDK の大版（Python v2.0.0・TypeScript v3.0.0）で入りました。

上の段が旧方式、下の段が新方式です。色の付いた箱が、矛盾（古い事実と新しい事実の食い違い）を扱う場所です。新方式も書込みの前に似た記憶を 10 件取りますが、使い道は抽出の文脈と重複の除去です。既存の記憶を書き換える判断には使いません。

### OSS の SDK で変わったこと

移行文書とリリースノート、現在の `mem0/memory/main.py` から確かめたことです。

- **書込みの結果**: `add()` が返す出来事は ADD だけになりました。旧版は ADD・UPDATE・DELETE を返していました。重複の除去は本文の MD5 hash の一致で、意味の判断はしません。
- **明示の操作は残る**: `update`・`delete`・`delete_all`・`history`・`reset` は今もあります。どれも LLM を呼ばず、履歴の表に UPDATE・DELETE を記録します。自動の更新・削除がなくなっただけで、利用者が呼ぶ操作として残っています。
- **グラフの削除**: `enable_graph` と `graph_store` の設定をなくし、Neo4j・Memgraph・Kuzu・Apache AGE・Neptune の driver とその処理（約 4,000 行）を除きました。OSS にグラフ記憶の代わりはありません。必要な利用者には、Platform へ移るか、新しい検索 API に合わせて作り直すよう案内しています。
- **実体**: 既存のベクトルストアの中に、並列のコレクション `{collection}_entities` を初回に自動で作ります。意味の近さが 0.95 以上なら既存の実体にまとめます。移行文書は、これをグラフ記憶とは別物だと明記しています。
- **検索**: 意味・BM25・実体の得点を正規化して 1 つの得点に融合します。ただし候補は意味検索の結果だけです。BM25 と実体は順位の加点にとどまり、候補を増やしません。spaCy がなければ意味検索だけになり、Qdrant で fastembed がなければ BM25 は黙って無効になります。
- **既定値**: `top_k` を 100 から 20 に、`threshold` をなしから 0.1 に、`rerank` を True から False に変えました。得点の範囲は [0, 1] のままで、計算の方法が変わりました。
- **指示文**: `custom_fact_extraction_prompt` を `custom_instructions` に改名し、更新の判断に使っていた `custom_update_memory_prompt` を非推奨にしました。

移行文書自身が、この変更の意味を次のように書いています。「ADD-only のため、記憶は時とともに溜まる。情報が変わると、新しい事実は古い事実と並んで保存される。順位は検索が担う」。

### Platform だけに足されたこと

- **時間推論**: 書込み時に別の処理で、出来事の時期、続いているか終わったか、日付の精度、記憶の種類（予定・状態・出来事・関係・好み・不在）を取り出します。続いている状態には state key を付け、同じ key の新しい状態が来ると、古い状態の終了時刻を自動で入れます。削除はしません。読み出しでは、追加の LLM 呼び出しなしで質問の意図（過去の範囲・今の状態・期間・予定・新しさ）を分類します。取得は絞らず、並べ替えで時間の得点を加えます。既存の記憶にはさかのぼって付けません。
- **記憶の減衰**: 検索時だけの並べ替えです。記憶ごとに最近 20 回の取得時刻を持ち、最近使われた記憶を最大 1.5 倍に、使われない記憶を 0.3 倍まで下げます。消しも隠しもしません。強さの調整は今の版ではできません。
- **グラフ記憶**: Platform の中で人・場所・概念をつなぎ、全プランで常に有効です。つながりは同じ記憶に現れること（共起）から推定し、型付きの関係は付けません。順位に効くだけで、応答の `relations` は常に空です。

## もたらすもの

最初に表でまとめます。「旧」は 2025 年の論文と旧 OSS、「新」は 2026 年 4 月以降の OSS と Platform です。「解釈」と書いた箇所は、文献からの私の推論です。

| 観点 | 旧 | 新 | もたらすもの |
| --- | --- | --- | --- |
| 書込みの費用 | 抽出と操作の判断で LLM が 2 段 | LLM 1 回 | 抽出の遅延はおよそ半分（mem0 の発表） |
| 古い記憶 | LLM が更新・削除する | 残る。新旧が並ぶ | 履歴が残る。今の事実を選ぶ仕事が読み出しへ移る |
| エージェントの発言 | 無視されがち | 利用者の発言と同じ重み | 約束を覚える。誤りも記憶になる |
| 訂正 | 書込みの判断で自動 | 明示の `update`・`delete` だけ | 訂正と忘却の設計がアプリケーションの責任になる |
| 関係 | Mem0g の型付きの関係（Neo4j） | 実体による順位の加点だけ | 関係を辿る質問には答えられない |
| 時間 | なし（Mem0g は古い関係を無効化） | Platform だけに時間推論と減衰 | 自前で運用するなら時間の扱いを自分で作る |
| 評価の軸 | 精度・遅延・token | 精度と、1 回の取得あたりの token | 小さな予算で答えることが目標になる |

### 1. 矛盾の解決が読み出しへ移る

いちばん大きな変化です。たとえば利用者が「引っ越した」と言ったとします。旧方式では、書込みの時点で LLM が古い住所の記憶を更新または削除しました。新方式では新旧の住所が両方残り、検索の順位で新しいほうが上に来ることを期待します。

順位で解決する方式には限界があります。

- 古い事実も新しい事実も質問に近いので、両方が回答するモデルに渡ります。どちらが今の事実かは、そのモデルの読解で決まります（解釈）。
- mem0 は「知識の更新は、加算型の構造にとっていちばん難しい分類のままだ」「古い事実が新しい事実の近くに出ることがある」と書いています。
- 数値にも出ています。時間推論を足した後の LongMemEval では、時間推論の分類が 93.2 から 97.0 に上がった一方、知識の更新は 96.2 から 93.6 に下がりました。BEAM では矛盾の解決が 35.7（1M token）と 32.5（10M token）で、公開された分類の中で最も低い値です。
- Platform の時間推論は、続いている状態に state key を付け、新しい状態が来ると古い状態に終了時刻を入れます。書込み時の判断を、削除ではなく「終わったと記す」形で一部戻したものと読めます（解釈）。この仕組みは OSS にはありません。

### 2. 書込みが安く、壊れにくくなる

- LLM の呼び出しが 1 回になり、抽出の遅延はおよそ半分になったと mem0 は書いています。
- 旧方式の 2 段目では、LLM が既存の記憶を書き換える権限を持っていました。誤った UPDATE や DELETE は、記憶を黙って失わせます。新方式にはこの経路がなく、書込みで既存の記憶が壊れません（解釈。mem0 は「何も消さない」と表現しています）。
- 重複の除去は本文の hash の一致だけです。言い換えただけの重複は残り、記憶の数は増え続けます。

### 3. エージェントの発言が記憶になる

- 旧方式は、エージェントの確認や提案を無視しがちでした。新方式は、利用者の発言と同じ重みで保存します。
- 利点は、エージェントが約束したことや、提案して利用者が受け入れたことを覚えられることです。
- 懸念は、エージェントの推測や誤りも、利用者が述べた事実と同じ重みで記憶になることです（解釈）。発言者の違いが順位にどう効くかは、発表に書かれていません。

### 4. 訂正と忘却がアプリケーションの責任になる

- 自動の更新・削除はなくなり、明示の `update`・`delete`・`delete_all` が残りました。利用者が「それは違う」「忘れて」と言ったとき、それを操作に変えるのはアプリケーションです。
- 第三者の評は「頻繁な更新と削除が要る用途には向かない」と書いています。mem0 自身も、「利用者はどう消すのか」をアプリケーションの側で決めることとして挙げています。
- 減衰は記憶を消さず、検索の並べ替えを変えるだけです。溜まり続ける記憶の量そのものは減りません。
- 消したい記憶を探すことも難しくなります（解釈）。同じ事実の言い換えや古い版がいくつもあると、「忘れて」に応えるには関係する記憶をすべて見つける必要があります。

### 5. 関係（グラフ）が順位の手がかりに縮む

- OSS は、外部のグラフ DB への対応を約 4,000 行ごと外しました。Platform のグラフ記憶も、共起からつながりを推定して順位に使うだけで、型付きの関係は返しません。
- 実体は順位の加点にとどまり、候補を増やしません。意味検索で取れなかった記憶を、実体を辿って見つけることはできません。
- 2025 年の論文でも、Mem0g は基本版より全体で約 2% 高いだけで、遅延は増えていました。グラフを保つ費用に見合わなかったという判断と読めます（解釈）。
- mem0 自身も、関係の出力を使っていた利用者にとっては後退だと書いています。

### 6. OSS と Platform の差が広がる

- 時間推論・減衰・グラフ記憶は Platform だけにあります。発表の数値は Platform の独自の最適化を含み、OSS では「方向は同じだが、同じ値にはならない」と mem0 は書いています。
- 自前で運用する利用者は、時間と矛盾の扱いを自分で作る必要があります。

### 7. 評価の軸が「小さな予算で答える」へ移る

- mem0 は、1 回の取得あたり約 7,000 token（全文脈を渡す方式は 25,000 以上）を前面に出し、「26,000 token を使う方式は本番では成り立たない」と書いています。
- 一方で、LoCoMo や LongMemEval のような小さなベンチマークは、取得を広げる、文脈を長くする、強いモデルを使うといった方法で、記憶の仕組みが良くならなくても点が上がると、mem0 自身が注意しています。100 万 token・1,000 万 token の会話を使う BEAM を重視するのはそのためです。
- mem0 の「State of AI Agent Memory 2026」は、残る課題として、時間の推論・記憶が古くなること・セッションをまたぐ同一性・プライバシー・削除・用途ごとの評価を挙げています。「多くのシステムは変化を置き換えとして扱う。正しくは進化として扱う」とも書いています。

| ADD-only、グラフの削除、実体のコレクション、既定値の変更 | 公式の移行文書、リリースノート、現在のソースコード | 高い |
| 明示の `update`・`delete`・`history` が残る | 現在の `main.py`（main 枝） | 高い。ただし版の番号との対応は未確認 |

### 数値を目安にとどめる理由

- Platform で測った値で、OSS にない独自の最適化を含みます（mem0 のブログ）。
- ブログは、回答と採点に使ったモデルを書いていません。評価の枠組み（memory-benchmarks）は公開されていて、既定の回答・採点モデルは gpt-4o、OSS でも Docker で動かせます。
- 採点の揺れで ±1 点の幅があると mem0 は書いています。
- ページによって値が食い違います。
  - LongMemEval の新しい値が 93.4・94.4・94.8 に分かれます。取得件数（top_200 と top_50）の違いと、時間推論を足す前後の違いが混ざっています。
  - 「旧アルゴリズム」の値が、比べる相手によって変わります。ブログの表では LoCoMo 71.4・LongMemEval 67.8、時間推論の記事では LoCoMo 86.1 や 91.6 を基準にしています。2025 年の論文の Mem0 は LoCoMo 66.88 です。
  - LoCoMo の時間の分類の変化が、記事によって -0.3 点と +6.7 点に分かれます。
- 2025 年の論文の値と 2026 年の値は、評価の条件が違うので直接は比べられません。
- mem0 自身が、LoCoMo や LongMemEval は記憶の仕組みが良くならなくても点が上がると注意しています。

### 日付について

- ブログに表示される日付（4 月 16 日など）と、ページの内部情報の日付（11 月 6 日）が食い違います。内部情報の日付は取得した時刻と見て、表示の日付を採りました。
- Python v2.0.0 の正確な公開日は確かめていません。リリースのページが「6 か月前」のような相対の日付しか出さないためです。

### 確かめていないこと

- memory-benchmarks を実際に動かした再現。
- 独立した第三者による比較。mem0 の記事は「第三者の比較が出始めている」と書きますが、名前を挙げていません。
- 時間推論が OSS に入っていないこと。mem0 は Platform のみと書き、第三者の評は含まれると書いています。この文書では mem0 の記述を採りました。

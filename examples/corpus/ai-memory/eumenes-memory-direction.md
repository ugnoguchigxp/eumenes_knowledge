# eumenes_memory はどうするべきか

## 結論

**mem0 の後を追わず、「書込みの前に確かめる台帳」という今の設計を保ちます。その上で、欠けている「多くの記憶から小さな予算で取り出す部分」を足し、品質を他と比べられる物差しで測ります。**

- **保つもの**: 確認つきの計画（plan から apply）、矛盾を保存せず確認に回すこと、誰の発言か（origin）の区別、忘却の依存閉包と journal。mem0 は ADD-only に移って、矛盾の蓄積と訂正・忘却の難しさを自ら課題に挙げています。そこは eumenes_memory がすでに解いている部分です。
- **足すもの（優先順）**:
  1. 想起の候補を絞る仕組み。全件が予算に収まる間は今のまま全件を渡し、収まらないときだけ候補を絞ります。絞ったことは必ず応答に書きます。
  2. 回答の品質の受入を終えること。根拠のない断定を 0 にし、独立した判定で確かめます。
  3. 公開ベンチマークでの測定。mem0 が最も弱い分類（知識の更新・矛盾の解決）を中心に、同じ回答モデルで mem0 OSS と並べます。
  4. 配布の管理。中身が変わるたびに版番号を上げ、clean な commit からだけ配布物を作ります。
- **進め方**: どれも合成データと公開データの examples で先に確かめます。実際の会話や文書は、利用者が決めるまで使いません。

## 前提

2 つの文書から、判断に効く事実だけを引き継ぎます。詳しい根拠はそれぞれの文書にあります。

**mem0 の転換から**（[mem0 のアーキテクチャ転換が何をもたらすか](https://claude.ai/artifact/S9HwwfJK7hFTuujn1RBmfz)）

- M1. mem0 は矛盾の解決を、書込み時の LLM の判断から読み出し時の順位へ移しました。その結果、知識の更新と矛盾の解決が最も弱い分類になっています（BEAM の矛盾の解決 35.7）。
- M2. 訂正と忘却は、アプリケーションが明示に操作するものになりました。mem0 自身が、プライバシーと削除を未解決の課題に挙げています。
- M3. 取り出しは、意味・キーワード・実体の 3 つの信号を融合し、1 回あたり約 7,000 token に収めています。小さな予算で答えることが評価の軸になりました。
- M4. 外部のグラフ DB は OSS から外され、実体は順位の手がかりに縮みました。
- M5. 時間については、Platform で「同じ鍵の新しい状態が来たら古い状態を終わらせる」書込み時の構造化に一部戻っています。
- M6. mem0 の数値は自社の Platform での測定で、条件が一部非公開です。ただし評価の枠組み（memory-benchmarks、Apache-2.0）は公開され、OSS でも動かせます。

**eumenes_memory の評価から**（[eumenes_memory の評価](https://claude.ai/artifact/D1qCmynFLCMfmbpeg4ei8X)）

- E1. 訂正・停止・忘却の区別、忘却の依存閉包と journal、矛盾を確認に回す計画は、設計として強い部分です。
- E2. 自然文の想起は許可範囲の全件を渡す方式で、合成の 1,001 件では上限の約 2.4 倍になり拒否されます。候補を絞る仕組みがありません。
- E3. 回答の品質の評価は 80 件中 30 件で止まり、根拠のない断定が 1 件以上あります。
- E4. 評価はすべて合成データで、公開ベンチマークでは測っていません。稼働中の実際の記憶は 0 件です。
- E5. 同じ版番号で中身の違う tgz があり、Eumenes 側の取り込みが未コミットです。

以下の施策には、どの前提から導いたかをこの記号（M1、E2 など）で添えます。

## やること

### 1. 想起の予算を守る候補の絞り込み（E2、M3）

いちばん優先です。記憶が数百件を超えると、今の方式では想起そのものが実行できなくなります。

- 送信全体が上限に収まる間は、今のまま全件を渡します。収まらないときだけ、候補を絞ってからモデルに渡します。
- 絞ったときは、応答に「全件ではない」と理由を付けて返します。eumenes_knowledge の `complete: false` と `partialReasons` と同じ考え方で、「記憶にない」と「候補から外れた」を区別できるようにします。黙って切り捨てないという今の原則は保ちます。

絞り方は、次の 2 つを examples で比べて決めるのがよいと考えます。

| 方式 | やり方 | 利点 | 懸念 |
| --- | --- | --- | --- |
| A. 目録で 2 段 | 1 段目で、各記憶の短い目録（ID・種類・対象・意味の鍵）だけをモデルに渡して選ばせる。2 段目で、選んだ記憶の本文と出典を渡す | 意味はモデル、予算はコードという今の分担のまま。索引が要らない | 目録も件数に比例して増える。モデルの呼び出しが 2 回になる |
| B. 索引と順位の融合 | 語の重なり（FTS5 の trigram など）・対象と種類の一致・ベクトル（任意）で候補を取り、順位だけで融合（RRF）して上位を渡す | mem0 の「複数の信号の融合」に当たる。eumenes_knowledge の検索と同じ作り方で、件数が増えても持つ | 索引という派生物が増える。言い換えを取りこぼすおそれ |

- 比べるときは、同じ fixture・同じ質問で事前に登録し、「正解の記憶が候補から落ちる率」と「送信の bytes」で決めます。
- 索引は本体（eumenes-memory）に戻さず、host か Eumenes の派生物として持ちます。本体は schema 8 で全文索引を外しており、その判断を守ります。
- 索引も記憶の写しなので、忘却の依存閉包に入れます。host はすでに自分の派生物を ExternalDependent として登録しているので、同じ仕組みに載せます。mem0 の文書はこの点に触れていません（M2）。

### 2. 回答の品質の受入を終える（E3）

- quality-80 の残り（80 件中 50 件の生成と採点）を、予算を取り直して終えます。
- 判定に、実装したエージェントとは別の判定者を入れます。たとえば、系統の違う 2 つのモデルの一致を一次判定にし、意見が割れたものだけを人が見ます。
- 根拠のない断定が 0 件であることを受入の条件にします。N013 のように「他人についての記憶から本人のことを断定する」誤りには、`other_person_note` と本人の記憶を回答で分けて扱う試験を足します。
- 取得から回答までを通した性能も測ります。

### 3. 公開の物差しを作る（E4、M1、M6）

- LongMemEval の「知識の更新」「時間の推論」「複数のセッション」と、BEAM の「矛盾の解決」を中心に、公開データの一部で測ります。どれも mem0 が弱い、または弱くなった分類で、書込みの前に確かめる設計が効くはずの所です（解釈。測って確かめます）。
- mem0 の memory-benchmarks を使い、自前で動かす mem0 OSS と、同じ回答モデル・採点モデルで並べます。mem0 の Platform の数値とは比べません。
- eumenes_memory は会話から自動で記憶を作らないので、会話を host の plan から apply に通す「取り込み役」を examples に作ります。本人の確認の段は、評価では自動の承認として扱い、そのことを記録に書きます。
- 費用の上限を先に決め、quality-80 と同じく予約の台帳で守ります。

### 4. 時間の問いを想起に渡す（M5）

- 質問が「今」を問うのか、「過去」や「期間」を問うのかを、想起の入力に明示します。それによって、superseded の版を使うかどうかを切り替えます。
- mem0 の Platform は、これを読み出し時の意図の分類で行っています。eumenes_memory は状態と版をすでに持っているので、意図を渡すだけで済む見込みです。

### 5. 配布の管理を正す（E5）

- 中身が変わるたびに版番号を上げます（例: 本体 0.0.5、host 0.1.1）。同じ版番号の tgz は 1 つだけにします。
- 配布物は clean な commit からだけ作り、manifest の commit と一致することを verify:package で確かめます。
- README の Seed の説明を、同梱している合成の 18 件（State に入るのは 10 件）に合わせて直します。

## やらないこと

mem0 の変更のうち、取り入れないものです。

| mem0 の変更 | 取り入れない理由 |
| --- | --- |
| ADD-only の書込み | 矛盾が溜まり、今の事実を選ぶ仕事が回答するモデルに移ります（M1）。eumenes_memory は確認つきの計画で、すでに矛盾を扱えています（E1） |
| エージェントの発言を本人と同じ重みにする | 推測や誤りが、本人が述べた事実と同じ扱いになります。origin の区別（`agent_inferred` は本人の確認で昇格）を保ちます |
| 外部のグラフ DB | mem0 自身が約 4,000 行ごと外しました（M4）。文書をまたぐ関係は eumenes_knowledge、世界の構造は World の領分です |
| 本体へのベクトル・全文検索 | 本体は判断しない台帳のままにします。索引は host か Eumenes に派生物として持ち、忘却の閉包に入れます |
| 使われない記憶の減衰による自動の忘却 | mem0 の減衰も並べ替えだけで、記憶を消しません。忘却は本人の明示の操作だけにします。並べ替えに使うかは、「やること」の 1 の比較で決めます |
| mem0 の数値を目標にする | 測定の条件が違い、ページの間でも値が食い違います（M6）。比べるなら、同じ条件で自分たちが測った mem0 OSS とだけ比べます |

## 段階と受入の条件

どの段も、合成データと公開データの examples で先に確かめます。Eumenes への反映は最後で、利用者が決めます。

S1 と S2 は並行して進められます。S3 は想起と回答が受入を満たしてから行います。先に測ると、既知の弱点を測るだけになるからです。S4 はいつでも行えますが、S5 の前に済ませます。

| 段 | 内容 | 受入の条件 |
| --- | --- | --- |
| S1 想起の予算 | 方式 A と B を事前登録で比べる。時間の意図を想起に渡す（やること 1・4） | 合成の 1,001 件で、全問が上限の内に収まる。正解の記憶の取りこぼし率を記録する。絞ったときは必ず partial と理由を返す。索引が忘却の閉包で消えることを試験で示す |
| S2 回答の品質 | quality-80 の残りを終える（やること 2） | 80 件すべてを生成し、独立した判定で採点する。根拠のない断定が 0 件 |
| S3 公開の物差し | 公開データの一部を、mem0 OSS と同じ条件で測る（やること 3） | 費用の上限の内で、選んだ分類の点数と条件を記録に残す。勝ち負けは受入の条件にしない |
| S4 配布と文書 | 版番号、clean な commit からの配布、README（やること 5） | 同じ版番号の tgz が 1 つだけ。verify:package で manifest の commit と一致する |
| S5 Eumenes へ | 利用者の判断で、新しい版を Eumenes に取り込む | 利用者の承認。実データの利用開始は別の判断 |

## eumenes_knowledge との関係

2 つのパッケージは、同じ作り方をしています。SQLite は Eumenes が持ち、LLM が判断してコードが照合し、出典を byte 範囲と digest で持ち、読める範囲を fail closed で限ります。統合はせず、所有と配布を分けたまま、契約と手法を揃えます。

### 揃えられるもの

コードの依存ではなく、契約と作り方の共有です。

- **順位の融合**: eumenes_knowledge の検索は、4 つの経路（全文・ベクトル・対象・関係）を得点ではなく順位だけで融合しています（RRF）。「やること」の 1 の方式 B は、この作り方をそのまま使えます。
- **完全さの契約**: `complete` と `partialReasons`（`route_skipped` など）。「絞ったら partial を返す」に同じ語彙を使えます。
- **根拠の状態の語彙**: knowledge は valid・stale・unavailable・mismatch・not_available、memory は current・stale・missing・unverified を使います。Eumenes の会話が両方を引用するなら、対応表を作って揃えます。

### 境界

- 文書の中の対象と関係、文書をまたぐ同一視は、eumenes_knowledge の領分です。mem0 が OSS から外したグラフの役割は、Eumenes では knowledge と World が持ち、memory には入れません。
- 本人についての記憶（好み・事実・制約など）は memory の領分です。
- 文書から本人の事実を記憶にするときは、knowledge の根拠（文書 ID・版・byte 範囲）を出典にして host の plan を通す、というつなぎ方が考えられます。ただしこれは未決です。
- どちらのパッケージも、Eumenes への反映は examples で十分に確かめてからです。

## 未決の判断

利用者が決めることです。私の推奨を添えます。

| 判断 | 推奨 |
| --- | --- |
| 想起の絞り込み（方式 A・B）の比較を始めるか | 始める。最も優先で、合成データだけで進められます |
| 索引を host と Eumenes のどちらに持つか | host。すでに自分の派生物を忘却の閉包に登録していて、CLI・MCP と会話で同じ想起を使えます |
| 公開ベンチマークに使う費用の上限と、回答・採点のモデル | quality-80 と同じく上限を先に決め、mem0 OSS と同じモデルにそろえます |
| Eumenes 側の未コミットの取り込み（本体 0.0.4 の `30721f30aa19`、host 0.1.0 の `3b6091d1b1ea`）をどう確定するか | S4 で版番号を上げた配布物に置き換えてから確定する |
| 実際の会話や記憶をいつ使い始めるか | 今は使わない。S1～S3 の受入を満たした後に改めて決めます |
| knowledge の文書の根拠を、記憶の出典として使うか | 後で。eumenes_knowledge の P4（CLI・MCP）の後に検討します |

# 関係名を後回しにして文書をつなぐ

文書をまたぐつながりは、LLM に断片ごとに関係名を書かせて作るのをやめ、**原文の断片そのもの、Markdown の明示的な構造、決定的に取った言及と断片の型なし二部グラフ、人の判断**の 4 つで作るのがよい。関係名は、利用者が辺を開いたときだけローカル LLM に根拠付きで付けさせる。英語の評価では、関係抽出をやめて「対象・文・段落」の包含だけでグラフを組んだ LinearRAG が、**索引時の LLM トークン 0** で HippoRAG 2 を多段質問の精度で上回った。同じ条件で LightRAG は入力 3,552 万・出力 5,116 万 token を使い、どの手法よりも遅かった ([LinearRAG](https://arxiv.org/html/2510.10114))。いまの「言及 600 件が辺 597 本、文書横断 0 本」という症状は、断片ごとに独立に関係を抽出すると全体で重複と衝突が起きる、という LinearRAG の指摘そのもので、関係名を整える指示を工夫しても直らない。同一視は、日本語の表記ゆれを Sudachi などで決定的なキーに落とし、名前の近さ・型・説明・名前の珍しさで採点する形に変える。ハードな「別物」の制約は、人の判断と明示構造からだけ取る。小さい LLM は同一かどうかの順位付けはできても判定の閾値がずれる、という 2026 年の結果があり ([Gopal et al.](https://arxiv.org/abs/2610.31407))、その different をそのまま cannot-link にしていることが、同じ名前が分かれる原因として有力だからである。この構成なら、普段の LLM の呼び出しは「曖昧な組への補助票」と「開かれた辺の命名」だけになり、取り込みの時間は文書量に比例する LLM の生成から外れる。文書が変わっても、変わった断片だけを処理し直せばよい。ただし、ここで勧める方式はどれも日本語で評価された公開結果がほとんどない。とくに、日英が混ざる技術メモから言及をどれだけ取りこぼさずに取れるかは確かめられていない。最初の一歩は、新しいモデルを入れずに、すでに取り込んだ 60 KB の言及へ決定的な正規化キーを当て、文書をまたぐ共有ノードが何本できるかを数えることである。

## 文書横断の辺が 0 本なのは、関係名を断片ごとに書かせる設計の帰結

LinearRAG の著者は、関係抽出を捨てた理由を 4 つ挙げている。否定文を肯定に読むような局所的な誤り。段落ごとに独立に抽出するため、コーパス全体で関係が衝突・重複する大域的な不整合。三つ組に落とすときに含意が失われること。そして、段落どうしをつなぐ主な錨は関係ではなく対象だということ ([LinearRAG](https://arxiv.org/html/2510.10114v4))。2 番目は、自由文の関係名が言及 600 件に対して 597 通りに散った今回の現象と同じである。LinearRAG は spaCy の固有表現抽出で取った対象と、文・段落との包含行列だけで「関係なし」のグラフを作り、Personalized PageRank（PPR）で段落を順位付けする。2WikiMultiHopQA の索引は **249.78 秒・LLM トークン 0** で、HippoRAG 2（1,147.01 秒、入力 498 万・出力 122 万 token）や LightRAG（**4,933.22 秒、3,552 万・5,116 万 token**）より速い。精度も 2Wiki の Contain-Acc で 70.20 と、HippoRAG 2 の 62.70 を上回り、HotpotQA・MuSiQue・医療のデータでも上回った ([LinearRAG](https://arxiv.org/html/2510.10114v4))。別のグループの比較でも、コーパス 100 万 token あたりの構築は LinearRAG が 0.68 時間・0 ドル、HippoRAG 2 が 1.19 時間・2.85 ドル、GraphRAG が 1.72 時間・13.19 ドルだった ([RAGSearch](https://arxiv.org/html/2604.09666v1))。

効いているのが関係の型ではないことは、ほかのアブレーションからも読み取れる。HippoRAG（2024）で抽出器を GPT-3.5 の OpenIE から REBEL に替えると、Recall@5 の平均は 72.9 から 58.4 に落ちた。著者はその理由を、ノードと辺がほぼ半分になって連想が欠けたためと説明している。PPR の遷移は関係名を使っていない ([HippoRAG](https://arxiv.org/html/2405.14831))。小さいモデル向けの MiniRAG では、LM が説明文を書いた辺を経由する検索を外しても、精度は **53.29 から 50.47** に下がっただけだった。索引構造を外したときの低下（53.29 → 26.02）よりはるかに小さい ([MiniRAG](https://arxiv.org/html/2501.06713))。KET-RAG では、LLM を使わないキーワードと断片の二部グラフだけで、MuSiQue の Coverage が単純なベクトル検索の 26.4 から 50.8 に上がり、LLM で作った骨格 KG だけの 43.4 も上回った。ただし EM では 7.0 と、骨格 KG の 11.0 に劣った ([KET-RAG](https://arxiv.org/html/2502.09304v2))。HippoRAG 2 の論文では、LightRAG の QA F1 平均は **6.6** で、密なベクトル検索の 57.0 を大きく下回った ([HippoRAG 2](https://arxiv.org/html/2502.14802v2))。さらに 2025 年の研究は、同じパイプラインで保存する表現だけを変えて比べた。原文の断片は、LLM で抽出した型付きの成果物を LoCoMo で **43.9% 対 28.0%**、LongMemEval-S で 67.4% 対 45.4% と上回り、精度は「ストアに原文がどれだけ残るか」に沿って動いた ([Fidelity Before Structure](https://arxiv.org/abs/2601.00821))。まとめると、グラフの価値は共有ノードによる接続の密度と、原文への戻りやすさで決まる。文書横断の辺が 0 本のいまのグラフは、検索に効く前提をそもそも満たしていない。

グラフがいつも効くわけでもない。ICLR 2026 の GraphRAG-Bench では、単純な事実検索で再順位付けつきのベクトル RAG が 60.92 を取り、MS-GraphRAG の 49.29 を上回った（HippoRAG 2 は 60.14 でほぼ並ぶ）。グラフが勝ったのは、複雑な推論（HippoRAG 2 の 53.38 対 RAG の 42.93）や文脈の要約だった ([GraphRAG-Bench](https://arxiv.org/html/2506.05690))。2026 年の RAGSearch でも、一般的な QA での GraphRAG の上積みは平均 **+0.47** にすぎず、多段質問では +27.23 だった ([RAGSearch](https://arxiv.org/html/2604.09666v1))。小さいモデルとの相性はさらに厳しい。LightRAG の精度は、gpt-4o-mini を 4B 以下のモデルに替えると **56.90 から 35.42** に落ち、GraphRAG はどの小型モデルでも有効な応答を返せなかった ([MiniRAG](https://arxiv.org/html/2501.06713))。GraphRAG-Bench は Qwen2.5 の 3B・7B・14B を比べ、グラフ RAG は標準の RAG よりモデルの大きさに敏感で、7B 前後が実用の下限だとしている ([GraphRAG-Bench](https://arxiv.org/html/2506.05690))。このライブラリの使い道に当てはめると、会話や coding agent への検索と引用は、原文断片へのハイブリッド検索が主経路になる。グラフは、候補の拡張、関連文書の探索、閲覧のための補助である（推論）。関係の型が本当に要るのは、「何が何に依存するか」「何が何を置き換えたか」のように関係の種類そのものを問う場面と、ビューアでの色分けである。どちらも、後で述べる遅延命名で必要なときに作れば足りる。なお、関連文書の探索や閲覧そのものを課題として評価したグラフ RAG のベンチマークは見つからなかった。ここで引いた結果はすべて英語の QA と要約である。

## 日本語の言及抽出は GiNZA と Sudachi を土台にし、専用モデルは型付けに回す

いまの抽出は、2 KB の断片 1 つに約 52 秒・出力約 2,800 token を使う。その大半は自由文の関係と逐語引用の生成だと考えられる（推論）。原文の位置を返す抽出器に替えれば、引用は生成物ではなく原文のオフセットそのものになる。日本語でその土台になるのは GiNZA と Sudachi である。GiNZA は 2026-09-30 に 5.3.0 が出た MIT ライセンスの spaCy 互換パイプラインで、固有表現や名詞句を spaCy の `Span` として文字オフセット（`start_char`・`end_char`）付きで返し、文節の API も持つ ([GiNZA GitHub](https://github.com/megagonlabs/ginza), [spaCy API](https://spacy.io/api/span))。一方で、拡張固有表現（ENE）の精度は `ja_ginza` で **53.9**、最大の `ja_ginza_bert_large` でも 70.8 にとどまる ([GiNZA docs](https://megagonlabs.github.io/ginza/))。種類を当てる主力ではなく、名詞句や文節の主辞を候補として取る役に向く。Sudachi は分割の単位を A・B・C の 3 段で選べ、各語に `normalized_form`（附属 → 付属 など）と同義語グループ ID を持つ。これで、言及を文書横断の共有ノードにまとめるキーをそのまま作れる ([sudachi.rs](https://github.com/WorksApplications/sudachi.rs), [SudachiPy API](https://worksapplications.github.io/sudachi.rs/python/api/sudachipy.html))。京大の KWJA は、固有表現（84.6〜85.9）に加えて述語項構造と共参照（78.6〜79.2）まで CPU で出す。ただし出力は KNP 形式で文字位置の記載がなく、速度の数値も公開されていない ([KWJA](https://github.com/ku-nlp/kwja))。GiNZA・KWJA とも CPU での絶対的な処理量の一次資料は見つからず、60 KB が何分で終わるかは手元で測るしかない。

型付けと関係の補助に使える小さい専用モデルは、エンコーダで範囲を取る GLiNER 系が中心である。GLiNER2 は 205M〜340M、後継の GLiNER2.5 は 74M〜287M（多言語向けは mDeBERTa の 287M）で、Apache-2.0 ライセンス。`include_spans=True` で位置を返し、空白で語を区切らない言語には文字単位の分割を勧めている ([GLiNER2 GitHub](https://github.com/fastino-ai/GLiNER2))。論文の CPU 計測はラベル 5〜50 個で 130〜208 ms だが、CPU の型番も系列長も書かれていない。表の比較相手から見て、分類タスクの値である可能性が高い ([GLiNER2 論文](https://arxiv.org/html/2507.18546))。英語のゼロショット NER は CrossNER の平均で 0.590 と、GPT-4o の 0.599 に並ぶ ([GLiNER2 論文](https://arxiv.org/html/2507.18546))。しかし多言語版を含めて、**日本語の公開評価は見つからなかった**。日本語の GLiNER として公開されている `vumichien/ner-jp-gliner` は F1 92.49 だが、非商用ライセンスで、学習と評価が同じ Wikipedia データセットなので参考値にとどまる ([HF](https://huggingface.co/vumichien/ner-jp-gliner))。多言語 NER を 7 つのベンチマークで比べた 2026 年の Otter 論文では、GLiNER-multi-v2.1 は macro F1 0.427 で、日本語単独の値は図にしかない ([Otter](https://arxiv.org/html/2601.06347))。また、`include_spans` の位置が文字単位かトークン単位か、SudachiPy の `begin()`・`end()` が文字単位かバイト単位かは、文書から断定できなかった。どちらにしても、UTF-8 のバイト範囲に変える層が要る。

関係名を残したい場合でも、固定のラベル集合に写すだけで集約の問題は構造的に消える。品質の面では、正解の対象を与えた関係分類で、専用エンコーダの GLiREL は未見ラベル 15 個のとき Wiki-ZSL で **73.91** を保ったが、GPT-4o は **41.57** まで落ちた ([GLiREL](https://arxiv.org/html/2501.03172))。ただし、対象の検出から通して評価すると、GLiNER-Relex の平均 micro-F1 は 25.6、GPT-5-mini は 22.1 で、どの方式でも絶対値は低い。GLiNER-Relex は GPU（L4）で 288 語の文書を 0.9 秒で処理し、GPT-5-mini の 64 秒の約 70 分の 1 だった。ただし CPU の値はなく、論文の本文と表の数値は何か所かで食い違う ([GLiNER-Relex](https://arxiv.org/html/2605.10108v1))。ローカル LLM に固定ラベルを選ばせるなら、書かせ方に注意が要る。0.5B〜1.7B のモデルに JSON スキーマの厳しい制約を掛けると、形式の妥当性は 61.5% から 100% に上がったが、中身の正答率は **19.7% から 11.0%** に下がった ([The Constraint Tax](https://arxiv.org/abs/2605.26128))。自由に書かせてから、後段で固定ラベルに写すほうが安全である。強いモデルを一度だけ使える条件は、ここで生きる。GLiNER2 自身が、GPT-4o で注釈した約 25 万例で学習されている ([GLiNER2 論文](https://arxiv.org/html/2507.18546))。自分の領域で微調整した Qwen2.5-0.5B が、関係抽出でゼロショットの GPT-5.4 を上回った（micro-F1 0.83 対 0.69）という 2026 年の報告もある。著者は、この差はモデルの強さではなく課題への適応の効果だとしている ([Sub-Billion, Super-Frontier](https://arxiv.org/abs/2606.22606))。日本語でこの道を試した結果は見つからなかった。

係り受けからルールで三つ組を作る方法もある。spaCy の依存構造で作った KG が、検索の判定で GPT-4o 抽出の KG の約 94%（61.87% 対 65.83%、密なベクトル検索は 50.80%）に達した例がある。ただし評価は英語の企業 1 社の領域だけで、処理時間の実測もない ([SAP 論文](https://arxiv.org/html/2507.03226))。日本語なら GiNZA の係り受けや KWJA の述語項構造で同じ形を作れるが、関係名は述語の表層形になる。集約には、Sudachi の正規化か固定ラベルへの写像が別に要る。NuExtract・Triplex・mREBEL のような生成型の抽出器は位置を返さないので、写した文字列を原文から探し直すしかない。いくつかは非商用ライセンスでもあり、バイト範囲の引用を前提にするこのライブラリには合わない ([NuExtract 2.0](https://huggingface.co/numind/NuExtract-2.0-2B), [Triplex](https://huggingface.co/SciPhi/Triplex), [mREBEL](https://huggingface.co/Babelscape/mrebel-large))。抽出器が決定的で断片の中で閉じていれば、文書が変わっても変わった断片だけを処理し直せばよい。版の断片をすべて抽出し直すいまの問題も、これで同時に消える。

## 同一視は決定的なキーと採点で決め、LLM の different をハード制約から外す

2025〜2026 年の KG やエージェントのメモリの実装を見ると、同一視の方式は 2 系統に分かれる。Microsoft GraphRAG と LightRAG は、名前（GraphRAG は名前と型）の完全一致でまとめ、LLM は説明文の要約にしか使わない。そのため、別名は取りこぼし、同じ名前の別物はまとめてしまう ([GraphRAG dataflow](https://microsoft.github.io/graphrag/index/default_dataflow/), [LightRAG issue #1323](https://github.com/HKUDS/LightRAG/issues/1323))。Cognee・Mem0・iText2KG・Neo4j は、名前の埋め込みの cosine が閾値（**0.6〜0.97 とばらばら**）を超えれば寄せる。別名は拾えるが、「1963 AFL Draft」と「1963 NFL Draft」のような近い別物を誤ってまとめる ([Cognee](https://docs.cognee.ai/guides/memify-entity-deduplication.md), [Neo4j blog](https://neo4j.com/blog/developer/property-graph-index-llamaindex/))。両者の間にあるのが Graphiti の段階制である。正規化した名前の完全一致がちょうど 1 件なら確定する。だめなら文字 3-gram の MinHash/LSH を使い、Jaccard が 0.9 以上なら確定する。それでも決まらない曖昧なものだけを LLM に回す ([Graphiti dedup_helpers.py](https://raw.githubusercontent.com/getzep/graphiti/main/graphiti_core/utils/maintenance/dedup_helpers.py))。ただし、そのあいまい一致は名前を a-z と 0-9 だけに正規化する。日本語の名前は空か極端に短くなって長さとエントロピーの門で落ち、すべて LLM に回る、とコードからは読める（推論）。既存の設計を借りるときは、日本語の正規化を自前で足す必要がある。

日本語の表記ゆれは、3 段で決定的にかなり吸収できる。文字の段は NFKC と neologdn 相当の規則（半角カナ、長音の連続、各種ハイフン、日本語の間の空白）である。ただし neologdn の既定はチルダを消すので、「1995〜2001年」が「19952001年」になる。この点は設定で避ける ([UAX #15](https://unicode.org/reports/tr15/), [neologdn](https://github.com/ikegami-yukino/neologdn))。語の段は Sudachi の `normalized_form` で、「附属」→「付属」、「SUMMER」→「サマー」、「シュミレーション」→「シミュレーション」のように寄せられる ([SudachiPy](https://pypi.org/project/sudachipy))。同義と訳語の段は Sudachi の同義語辞書で、「インフルエンザ」と「influenza」が同じグループに入り、各語に対訳・別称・略語・表記ゆれの種別が付いている ([SudachiDict synonyms](https://github.com/WorksApplications/SudachiDict/blob/develop/docs/synonyms.md))。この辞書は一般語が中心で、チーム固有の製品名は載っていない。それでも同じ CSV の列の設計は、人が足す別名の保存形式にそのまま使える。正規化の結果は辞書の版で変わるので、キーには辞書の版も記録する。

名前に共通する文字がない別名（日本語名と英語名、略称と正式名）は、文字の比較では原理的に拾えない。候補を出す経路は、名前の埋め込みの近傍、別名の辞書、翻字の 3 つになる。埋め込みについては、multilingual-e5-small は文単位の言語横断検索で LaBSE に大きく劣る（Tatoeba の 112 言語平均で **64.2 対 81.1**） ([Multilingual E5](https://arxiv.org/html/2402.05672))。cosine は学習時の温度の都合で 0.7〜1.0 に集まるので、絶対値ではなく順位で見るよう model card が勧めている ([multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small/raw/main/README.md))。Cognee の文書も、「NYC」と「New York City」を拾うには閾値を 0.85 から 0.6 まで下げる必要があるとしている ([Cognee](https://docs.cognee.ai/guides/memify-entity-deduplication.md))。日英の固有名を e5・LaBSE・BGE-M3 で照合した精度を直接報告した資料は見つからなかったので、ここは自前の評価が要る。評価にも辞書にも使えるのが、Wikidata から作った多言語の名前対訳 ParaNames 1.0（約 1.4 億の名前、1,680 万の対象）である ([ParaNames 1.0](https://huggingface.co/papers/2405.09496))。日英の組の件数は確認できていない。辞書にない固有名のカタカナと英語は、カタカナを音素経由で英語側に寄せて照合するのが最良だった、という 2018 年の比較がある ([Yamashita et al.](https://aclanthology.org/W18-5809/))。そして最も確かな別名の出どころは、文書の front matter に人が書いた `aliases` である。

候補を出したあとの採点には、確率的レコードリンケージのライブラリ Splink のやり方を借りられる。ラベルなしの EM で比較列ごとの重みを推定し、名前の頻度で完全一致の重みを補正する。よくある名前の一致は弱い証拠、珍しい名前の一致は強い証拠になるので、「設計」や「API」のような頻出語での同名異物を抑えられる。新しい集合と既存の集合の間だけで採点する `predict_between` は増分のための API で、各組の判断にどの列が何点寄与したかを図で示せる ([Splink](https://github.com/moj-analytical-services/splink), [Splink TF guide](https://moj-analytical-services.github.io/splink/topic_guides/comparisons/term-frequency.html), [Splink inference API](https://moj-analytical-services.github.io/splink/api_docs/inference.html))。ただし、短い言及（名前と説明）に使った精度の報告はない。また、名前の cosine と説明の cosine のように相関する列は証拠を二重に数えるので（推論）、少数のラベルで較正する必要がある。束ね方は、正の辺でつながる連結成分ではなく、負の辺を重み付きで扱える相関クラスタリングがよい（Pivot 系は期待値で 3 近似） ([Single-Pass Pivot](https://arxiv.org/pdf/2305.13560))。いまの方式で同じ名前が分かれる理由も、ここから説明できる。文字体系をまたぐ人名の組の判定で、Qwen2.5-7B が同一の組を同一と答えた割合は、ラテン文字で **35.1%**、デーヴァナーガリーで 8.5% にすぎなかった。別人の組は 98% を超えて正解した。一方で、同一の組を上位に並べる力（**AUROC 0.925**）は残っていて、単純な較正で balanced accuracy の差の 87% を取り戻せた ([Gopal et al.](https://arxiv.org/abs/2610.31407))。小さい LLM の判断は、順位としては使えても、ラベルとしては「別物」の側に偏る。その different をハードな cannot-link にすると分裂が起きる。ハードな制約は確度の高いものに限るのがよい。人の訂正、明示構造（`aliases` や同じ ID）、型の明らかな矛盾、同じ文書の中で並べて比べられている 2 者などである。LLM の判断は、由来付きの弱い票として採点に入れる（推論）。

人の手間は、能動学習で小さく保てる。ER では、能動学習で選んだ 100 組で、全 894 組で学習したのと同じ性能になったという報告がある ([Kasai et al. 2019](https://preview.aclanthology.org/fix_video/P19-1586.pdf))。確認の列は、「採点が閾値の近く」「1 つの訂正で大きなまとまりが分かれたりつながったりする、橋になっている組」「頻出の名前」の順に並べればよい（推論）。強いモデルで一度だけ銀ラベルを作るのも有効だが、人の確認は必ず挟む。自動で作った翻字照合のラベルが人手と約 75% しか一致せず、人手で検証し直した例がある ([Entity_Identification](https://github.com/Multilingual-entity/Entity_Identification))。訂正は、Cognee のように重複ノードを消す不可逆な統合にしない ([Cognee](https://docs.cognee.ai/guides/memify-entity-deduplication.md))。「言及 → まとまり」の対応を毎回計算し直せる派生の表にしておけば、後からの分割も安全にできる。新しい言及は既存の代表と比べ、影響を受けた連結成分だけを束ね直せば増分で済む。Graphiti・Cognee・iText2KG も、新規と既存を比べるだけで、全体は束ね直さない。

## LazyGraphRAG からは索引だけを借り、問い合わせ時の LLM ループはローカルに載せない

問い合わせ時に LLM を回す方式の代表は、Microsoft の LazyGraphRAG である。索引は名詞句の抽出と共起、グラフ統計による階層的なまとまりだけで作り、LLM を使わない。索引の費用は **ベクトル RAG と同じで、通常の GraphRAG の 0.1%** とされる ([MSR blog](https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/))。LLM の仕事はすべて問い合わせ時に回る。3〜5 個の下位の質問を作り、文単位の関連判定を行い（1 問あたり 100・500・1,500 回の予算）、主張を抽出してまとめる。Microsoft の評価では、全体を問う質問で、GraphRAG の Global Search と同等の品質を 700 分の 1 以下の問い合わせ費用で出した。ただし評価は自社によるもので、AP ニュース 5,590 本と合成した質問 100 件だけである。勝率の数値もモデル名も公開されていない ([MSR blog](https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/))。独立の GraphRAG-Bench では、小説データの事実検索が **51.65** で、再順位付けつき RAG の 60.92 を下回った。医療のデータでは、4 種類の課題のうち 3 つで RAG に負けた ([GraphRAG-Bench](https://arxiv.org/html/2506.05690))。同じベンチの索引費用の表は LazyGraphRAG に 59 万 token を計上しており、「索引に LLM を使わない」という説明と合わない。再実装だった可能性がある。公開の状況も弱い。技術は Microsoft Discovery と Azure Local のプレビューに入ったとされる一方、オープンソースの `microsoft/graphrag` は README で「largely in maintenance mode」と書いており、索引方式の文書にも LazyGraphRAG は載っていない ([GitHub](https://github.com/microsoft/graphrag), [GraphRAG docs](https://microsoft.github.io/graphrag/index/methods/))。

この前提で、問い合わせ時の LLM ループを回すのは難しい。1 問あたり数百回の関連判定は、2 KB の抽出に 52 秒かかるローカルモデルでは対話の待ち時間に収まらない（推論。短い関連判定 1 回の時間は未計測）。クラウドのモデルに回せば、問い合わせの量に比例して費用が増える。最終的な文脈は LLM が抽出した主張で、原文の範囲ではないので、バイト範囲の引用にはもう一段の照合も要る。オープンソースの「fast」方式（NLTK や spaCy の名詞句と共起の辺）でも、まとまりの報告書を LLM で書く部分が残る。既定の抽出器は主に英語向けで、グラフは「quite a bit noisier」とされるだけで、品質の低下量は公開されていない ([GraphRAG docs](https://microsoft.github.io/graphrag/index/methods/))。借りるべきなのは 2 つである。名詞句の共起という LLM なしの索引と、LLM の仕事を必要になる瞬間まで遅らせるという考え方だ。後者の延長に EffiRAG がある。グラフは答えの根拠になる段落を探すためだけに使い、答えは原文から作る。UltraDomain の 120 問で LightRAG-hybrid より好まれた問いは **93 対 7**（引き分け 20）で、取り込みと問い合わせを合わせた費用は 57% 減った ([EffiRAG](https://arxiv.org/abs/2609.18099))。ホストの coding agent のように、問い合わせ側にすでに強いモデルがいる場面もある。そこではライブラリはグラフを辿る道具を出すだけにして、どこまで広げるかは相手に任せればよい。ライブラリ自身の運用費は増えない（推論）。

関係名の遅延命名も、この延長にある。索引時には、共有ノードと根拠の範囲（UTF-8 のバイト範囲）だけを持つ。ビューアで利用者が辺を開いたら、まず根拠の原文を並べる。「関係を説明」を押したときだけ、ローカル LLM に上位数件の根拠を渡して関係名と一文の説明を作らせ、引用と由来を付けてキャッシュする（推論による設計）。先例は CovidDEER である。文中で共起する対象の組ごとに係り受けの経路で文を採点し、閾値 0.7 を超えた文を辺の「関係の記述」にする。そのうえで上位 5 文から ChatGPT に短い要約を書かせ、利用者には生成文より元の文を確かめるよう勧めている。著者による 20 件の忠実性評価は 5 点満点で 4.10 だった ([CovidDEER](https://arxiv.org/html/2310.11681))。タンパク質のデータベース STRING も、共起による関連は相互作用の種類を決めない「機能的な関連」として扱い、根拠ごとの寄与を辺のポップアップで見せている ([STRING](https://string-db.org/help/scores/))。この方式なら、LLM の呼び出しは開かれた辺の数に比例するだけになる。ただし、辺を開いたときだけ関係名を作る方式を利用者で評価した研究や製品の文書は見つからなかった。

## Markdown の明示構造は精度ほぼ 1 の骨格だが、量は書き手次第で桁が変わる

Obsidian・Logseq・Org-roam・Dendron・Quartz などは、どれも人が書いた構造をそのまま辺にしている。型付きのリンクの書き方は 3 系統に収まる。front matter のキーに `"[[Note]]"` を書く形（Obsidian の Properties）、`Key:: [[Note]]` の行内フィールド（Dataview）、`- relation [[Note]]` のリスト行（Juggl の前身）である。Breadcrumbs は「A が B の up なら B は A の down」のような規則で暗黙の辺を足し、推移の規則を利用者が定義できる ([Obsidian Properties](https://obsidian.md/help/properties), [Dataview](https://blacksmithgu.github.io/obsidian-dataview/annotation/add-metadata/), [Breadcrumbs](https://github.com/SkepticMystic/breadcrumbs))。Org-roam は SQLite を「cache」と呼んで Org ファイルを正本にし、保存のたびにそのファイルの分だけ索引を更新する。別名は `ROAM_ALIASES` で、一意キーは `ROAM_REFS` で、文書の中に宣言させる ([Org-roam manual](https://www.orgroam.com/manual.html))。正本を別のサービスが持ち、ライブラリは派生の索引だけを持つという今回の前提と同じ形である。明示の辺は書き手の意図なので、**精度は定義上ほぼ 1** である。ファイル・行・キーの位置がそのまま引用の根拠になり、文字列の完全一致で成り立つので言語にも依存せず、ファイル単位で LLM なしに増分更新できる。

弱点は量である。利用者全体のリンク密度を調べた統計は見つからず、手に入るのは熟練者 1 人の分析くらいだった。8,053 ノート・内部リンク 64,890 本（平均約 8 本）の vault でも、リンクは目次ノート（平均 90.1 本）や月次ノート（161.6 本）に偏り、**普通のノートは 2.9 本**だった ([dsebastien](https://www.dsebastien.net/personal-knowledge-management-at-scale-analyzing-8-000-notes-and-64-000-links/))。チームの議事録や設計メモではもっと少ないと考えられ（推測で、統計はない）、明示構造だけで十分な密度は期待できない。見出しはほぼすべての Markdown 文書にあり、タグやフォルダも弱い構造として使える。本文中の名前と文書のタイトルを結ぶ「未リンクの言及」は、Org-roam が遅さを理由に既定で切っている ([Org-roam manual](https://www.orgroam.com/manual.html))。語の境界がない日本語では、「AI」や「設計」のような短いタイトルで誤りが増える。Sudachi の語境界での一致と最小の長さを条件にした、提案にとどめるのがよい（誤検出の実測報告は見つからなかった）。

辺は由来で分けて持つ。文書に書かれていた辺、規則で導いた辺（根拠の明示の辺を指す）、埋め込みや LLM による提案の辺、人がビューアで判断した辺の 4 つである。エージェントが正本を書く運用も広まった。Karpathy の LLM Wiki のように、生の資料は不変にして、wiki の層をエージェントが持つ形である ([Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f))。このため、正本のリンクを人が書いたかエージェントが書いたかは、ライブラリからは区別できない。由来は「文書に書かれていた」と「人が判断した」を別の値にするのがよい（推論）。人の判断を再索引のあとも残す方法には先例がある。OpenRefine は照合の判断と元の文字列を同じセルに持ち、同じ元の文字列を持つセルに一括で当てられる ([OpenRefine](https://openrefine.org/docs/manual/reconciling))。Wikidata は「別物である」（P1889）を明示のデータとして持ち、統合の道具がそれを見て誤った統合を止める ([Phabricator T141845](https://phabricator.wikimedia.org/T141845))。この 2 つにならい、判断は文書から派生する ID ではなく、正規化した名前・文書・引用文字列のハッシュのような内容のキーで保存する。文書が変わったら引用を照合し直し、照合できない判断は確認待ちに回す（推論）。人と LLM の組み合わせについては、4,100 万件の KG を検証した 2025 年の研究がある。LLM を足すと precision は 12% 上がったが recall が落ち、F1 は 5% 下がった。人と LLM を組み合わせると、少ない人手で F1 が 5% 上がった（要旨からの数値で、本文は未確認） ([Tsaneva et al. 2025](https://oro.open.ac.uk/103792))。

閲覧については、Obsidian の利用者の声と既存ツールの設計が一致している。全体グラフはノートが増えると役に立たず、使われるのは起点の近傍（深さ 1〜2）だという点である。ただし定量的な利用者研究は見つからず、根拠はフォーラムの声である ([Obsidian forum](https://forum.obsidian.md/t/how-do-you-use-the-graph-view/2785))。共起の辺は、期待値で割る正規化（NPMI や association strength）でどこにでも出る語を抑え、統計的に有意な辺だけを残す disparity filter のような方法で間引く。disparity filter は、米国の空港網で辺を 17% に減らして重みの 80% を残したとされる（検索結果の要約からの数値） ([Serrano et al.](https://arxiv.org/abs/0904.2389))。型付き関係がないぶん、辺の色は根拠の種類（明示のリンク、共有の対象、共有のキーワード、埋め込みの近さだけ）で分ければよい（推論）。ビューアの訂正の操作は、OpenRefine と同じように、スコア順の候補に対する same・different・skip と、辺の採用・却下があれば足りる。

## 勧める組み合わせと試す順番

### 6 つの方式を 5 つの軸で比べる

| 方式 | ローカル運用の費用 | 日本語 | 増分更新 | 引用根拠との相性 | 報告された品質 |
|---|---|---|---|---|---|
| いまの方式（LightRAG 風の LLM 抽出と LLM 同一視） | 2 KB に約 52 秒、60 KB に約 2 時間。LightRAG は独立の計測で索引費用が最も高い | モデルの判断と指示の言い方に左右される | 版の断片をすべて抽出し直す | 逐語引用を生成してから照合する | 小型モデルで LightRAG の精度は 56.90 → 35.42。関係が集約されず文書横断 0 本 |
| 小さい専用モデルの抽出（GiNZA・Sudachi・KWJA、GLiNER2/2.5、GLiREL） | CPU で動く。GLiNER2 は 130〜208 ms（条件不明）、GLiNER-Relex は GPU で 288 語 0.9 秒 | GiNZA・KWJA は日本語専用。GLiNER の多言語版は日本語の評価なし | 断片の中で閉じ、変わった断片だけ処理し直せる | 文字オフセットを返す（バイト範囲への変換が要る）。生成型は位置を返さない | GiNZA の ENE 53.9〜70.8、KWJA の NER 84.6〜85.9。通しの関係抽出は micro-F1 25.6 |
| 問い合わせ時に LLM を回すグラフ RAG（LazyGraphRAG） | 索引はベクトル RAG 並み。問い合わせごとに 100〜1,500 回の関連判定 | 評価なし。既定の名詞句抽出は英語向け | 共起表は安く更新できる。まとまりは再計算 | 文脈が LLM の主張なので、照合し直す段が要る | 自社評価では優位。独立の評価では事実検索で RAG に劣る（51.65 対 60.92） |
| LLM に頼らない同一視（正規化キー、候補生成、採点、相関クラスタリング） | Splink はノート PC で約 100 万件を約 1 分 | 表記ゆれは Sudachi で強い。共通文字のない日英の別名は埋め込みと辞書頼みで、e5-small の言語横断は弱い | 新規と既存の間の採点で済む | 判断ごとに、どの比較が何点寄与したかを示せる | 短い言及での評価なし |
| 型付き関係を持たないグラフ（言及と断片の二部グラフ、PPR、共起、埋め込みの近傍） | LLM 0。LinearRAG は 2Wiki の索引が 249.78 秒（LightRAG は 4,933 秒） | 固有表現抽出を日本語用に差し替える必要があり、評価なし | 行と列の追記で済む。PPR は問い合わせ時に計算 | 文ノードや断片が原文の範囲そのもの | 英語の多段質問で HippoRAG 2 以上。キーワード二部グラフで Coverage 26.4 → 50.8 |
| Markdown の明示構造と人の訂正 | パーサだけ | 文字列の一致なので言語に依存しない | ファイル単位 | 行・キーの位置で正確 | 精度は定義上ほぼ 1。量は普通のノートで 2.9 本/ノート（1 人の例） |

表を縦に読むと、決定的な 4 つの方式（専用モデルの抽出、LLM に頼らない同一視、型なしグラフ、明示構造）は、費用・増分更新・引用の 3 つの軸でいまの方式より明確に有利である。弱いのは日本語での実証だけだ。問い合わせ時に LLM を回す方式は索引が安いが、費用が索引から問い合わせへ移るだけで、ローカル運用ではその問い合わせ側が重い。

### 推奨する構成

答えと引用の土台は、原文の断片へのハイブリッド検索にする。まだなければ、Sudachi で分かち書きした BM25 を e5 に足す。その上に 3 つの層を重ねる。1 層目は、Markdown の明示構造（リンク、タグ、front matter のリンク値と `aliases`、見出しの階層、行内フィールド）を、バイト範囲と由来「文書に書かれていた」付きで辺にしたものである。2 層目は、GiNZA と Sudachi で決定的に取った言及（名詞句、文節の主辞、固有表現）と断片・文の二部グラフである。言及は正規化キーと採点・相関クラスタリングで文書横断のノードにまとめ、ノードの重みは出現する断片数の逆数や NPMI で付ける。関連文書は、起点の文書のノードを種にした PPR と、e5 の相互近傍（順位で切る）の 2 つの信号で出す。e5 の model card は、類似度やクラスタリングのような対称の用途では両側に「query: 」を付けるよう勧めている。検索用に「passage: 」で埋め込んだ断片を近傍グラフに流用せず、近傍グラフ用に埋め込み直す（推論） ([multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small/raw/main/README.md))。3 層目は、提案の辺と人の判断である。日々の運用でローカル LLM が担うのは、曖昧な同一視の組への弱い票（モデルと指示の版の由来付き）と、開かれた辺の命名と説明の 2 つに絞る。強いモデルは一度だけ、対象の型の集合（と、必要なら固定の関係ラベル）の設計と、評価集合の銀ラベルづくりに使う。日英が混ざる技術メモで GiNZA の再現率が足りないと分かった場合の後退策は、ローカル LLM に言及の名前と位置だけを出させ、関係は書かせないことである。出力の大半を占める関係の文がなくなるので、取り込みは大きく縮む見込みがある（推論。未計測）。

この勧めの前提のうち、確かめられていないものをはっきりさせておく。GiNZA・Sudachi・GLiNER 系が日英の混ざる技術メモ（英字の製品名、コード識別子）から言及をどれだけ取れるか。multilingual-e5-small が日英の固有名の別名をどれだけ近傍に入れるか。e5 の 512 token の上限を 2 KB の日本語断片が超えるかどうか（超えれば末尾が埋め込みに入らない）。型なしグラフや PPR が日本語や個人ノートの規模で効くかどうか。関連文書の推薦を人が評価した結果。遅延命名を利用者がどれだけ使い、どれだけ信頼するか。どれについても公開の評価は見つからなかった。英語の結果から方向は言えても、大きさは手元で測るしかない。

1 段目を最初に置くのは、この報告の中心の仮説を、新しいモデルも LLM の再実行もなしに数分で確かめられるからである。中心の仮説とは、「文書横断のつながりは、関係名ではなく、正規化した共有ノードから生まれる」というものだ。ここで文書横断のノードが十分にでき、人の確認でもまとまりが正しければ、2 段目以降に進む価値がある。逆に、ノードがほとんどできなければ、2 つの可能性を切り分ける必要がある。1 つは、素材の文書どうしが実際に共有する対象が少ないこと（60 KB という小さな素材では十分ありうる）。もう 1 つは、LLM が抽出した名前の表記が揺れすぎていること。前者なら方式の問題ではなく素材の規模の問題で、数百文書の素材で測り直す必要がある。また、キーでまとめた組の中に「設計」や「API」のような頻出語の同名異物がどれだけ混ざるかも、この段で見えてくる。名前の頻度による重みの補正が要るかどうかも、ここで判断できる。

## 結論

このライブラリが持つべき「知識グラフ」は、三つ組の集まりではない。**共有ノード、原文の範囲、由来付きの判断からなる根拠の索引**であり、関係名や説明は、その上に必要なときだけ作るキャッシュの見え方にすぎない。こう捉え直すと、LLM の役割は構造の書き手から、呼ばれたときだけ働く注釈者に変わり、その出力はハードな制約ではなく弱い票として扱われる。代わりに、量は少なくても確度の高い人の判断が最も価値のある信号になる。したがって設計の要は、人の判断を再索引のあとも生き残る内容のキーで保存することにある。すでに由来付きで判断を保存している今の設計は、この転換にそのまま使える。変えるのは、LLM の different を制約から票へ格下げする 1 か所である。

もう一つの含意は、残る不確かさの性質である。文献が答えてくれないのは、日英の混ざる技術メモでの言及の再現率と、小さい多言語埋め込みでの日英の別名照合の 2 点だけだ。どちらも手元の素材と数百組の評価集合があれば、数日で測れる。英語のベンチマークをこれ以上探しても判断は変わらない。測る前に作り込むべきなのは、抽出器や埋め込みモデルを差し替えても、評価集合と人の判断がそのまま使える形の保存の仕組みのほうである。

# グラフ作りを止め、検索の実力を先に測る

Neo4j・Memgraph・FalkorDB・Kùzu とその上に載る GraphRAG ツール、グラフを使うエージェント記憶の製品を調べると、**文書をまたいでエンティティどうしを結ぶ辺は、どの製品でも gpt-4o-mini 級の LLM が構造化出力で書いている**。LLM なしで張られる辺は、どの製品でもほぼ同じ 4 種類に限られる。文書→チャンクとチャンクの並び、埋め込みの近傍、パーサや表の外部キーのように宣言された構造、小型エンコーダで取った「対象がこのチャンクに出る」という言及である。弱いローカル LLM での抽出品質を公表した製品は一つもない。Graphiti と Cognee は、小さいモデルでは取り込みが失敗すると自ら書いている。効果を独立に評価した研究では、単一の事実や詳細を問う質問で素の RAG が互角以上だった。グラフが勝つのは多段・時系列・比較・全体の要約に限られ、しかも RAG にグラフと同じ量の文脈を渡すと差はほぼ消える（**71.01 対 71.17**）。Mem0 は 2026-04 に OSS からグラフ記憶を外した。eumenes_knowledge は、製品が LLM なしで作れる層（文書構造、全文索引、埋め込み、著者が書いたリンク）をすでにほぼすべて持っている。残る層は強い LLM を前提にしている。チームの実測（共起の辺で「深い」のは 12〜31%、共有名を介すと各文書が平均 420/422 文書とつながる）も、この素材ではその先に識別力のある信号が残っていないことを示した。したがって、**知識グラフとしての継続は勧めない**。意味が残りうるのは「原文断片のハイブリッド検索と引用の検証」だけだが、その品質は実文書・実際の質問・実ベクトルで一度も測られていない。記録にある recall@10 95.3% は台本どおりの fixture と意味のない擬似ベクトルで出た値で、判断の材料にならない。次にやることは一つでよい。実際の質問 20〜30 問で、FTS・埋め込み・ハイブリッドと「強いエージェントが生の Markdown を grep する」を比べる。ハイブリッドが FTS と grep を明確に上回らず、弱いローカル LLM の正答も増えなければ、ライブラリとしての開発はやめてよい。

## エンティティどうしの辺は、どの製品でも gpt-4o-mini 級の LLM が書いている

Neo4j の LLM Knowledge Graph Builder の処理は 2 段に分かれる。原典を `Document` にし、分割したチャンクを文書と前後のチャンクにつなぎ、埋め込みの近いチャンクどうしに kNN の `SIMILAR` を張る。ここまでは LLM を使わない。エンティティと関係は、そのあと LangChain の LLMGraphTransformer か有料 API の Diffbot が作る ([Neo4j Labs](https://neo4j.com/labs/genai-ecosystem/llm-graph-builder/))。公式の Python パッケージ neo4j-graphrag-python でも、LLM が要るのは関係の抽出と、テキストからのスキーマ推定の 2 か所だけである。分割・埋め込み・lexical graph と、完全一致・RapidFuzz・spaCy の埋め込みによる同一視は LLM なしで動く。ただし、LLM を使わない抽出器は同梱されていない ([User Guide: KG Builder](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_kg_builder.html))。LlamaIndex の PropertyGraphIndex は、既定で LLM の三つ組抽出器と `ImplicitPathExtractor` を併用する。後者はパーサが付けたノード間の関係をそのまま辺にするもので、「LLM も埋め込みモデルも要らない」と明記されている ([LlamaIndex](https://developers.llamaindex.ai/python/framework/module_guides/indexing/lpg_index_guide/))。FalkorDB の GraphRAG-SDK（2026-04 に 1.0、2026-08 時点で 1.3.0）は、散文の三つ組抽出と、文書をまたぐ重複の判定（LLM judge）に LLM を使う。LLM を一度も呼ばないのは、CSV などの表を `TableMapping` で宣言し、行と外部キーを辺にする経路だけである ([GraphRAG-SDK README](https://github.com/FalkorDB/GraphRAG-SDK), [Structured Ingestion](https://docs.falkordb.com/graphrag/structured-ingestion.md))。

3 社の中で、散文から LLM なしで辺を張る経路を既定にしているのは Memgraph だけである。AI Toolkit の `unstructured2graph` は、2025-11 の発表時には LightRAG による LLM 抽出だった。2026 年の既定はローカルの GLiNER2（`fastino/gliner2.5-base-v1`、194M パラメータ）で、API キーは要らない ([memgraph/ai-toolkit](https://github.com/memgraph/ai-toolkit), [Memgraph blog](https://memgraph.com/blog/unstructured-text-to-entity-graphs-rag-tool))。ただし既定のオントロジーには関係の型がない。そのため張られる辺は、対象とチャンクを結ぶ `MENTIONED_IN` と、チャンクの並びの `NEXT` だけになる。関係の型を書いたオントロジーを与えれば GLiNER2 でも型付きの関係を取れるが、品質の数値は公開されていない。既定のモデルのモデルカードには「Language: English」とある ([unstructured2graph README](https://github.com/memgraph/ai-toolkit/tree/main/unstructured2graph), [HF: gliner2.5-base-v1](https://huggingface.co/fastino/gliner2.5-base-v1))。Kùzu は文書からグラフを作る道具を自分では持たず、LlamaIndex・LangChain・BAML による LLM 抽出の保存先だった。その本体は **2025-10-10 にアーカイブ**された ([kuzudb/kuzu](https://github.com/kuzudb/kuzu))。Apple が Kùzu Inc. を買収していたことは 2026-02 に報じられた ([MacRumors](https://www.macrumors.com/2026/02/11/apple-acquires-new-database-app/))。Graphiti は Kùzu の driver を非推奨にし ([Graphiti README](https://github.com/getzep/graphiti))、Cognee は既定のストアを fork の LadybugDB に替えた ([Cognee docs: Ladybug](https://docs.cognee.ai/guides/ladybug))。Kùzu 公式の抽出デモで比べられたのも、商用の 4 モデルだけだった ([baml-kuzu-demo](https://github.com/kuzudb/baml-kuzu-demo))。

エージェント記憶の製品は、LLM への依存がさらに深い。Graphiti は episode ごとに、実体の抽出、振り返り、同一視、事実の抽出、辺の重複判定、時刻の抽出、矛盾による失効を、別々の LLM 呼び出しで行う ([Zep paper](https://arxiv.org/html/2501.13956))。利用者の計測では、150〜250 語の会話 1 件あたり **約 22 回**呼んでいた ([issue #467](https://github.com/getzep/graphiti/issues/467))。Cognee は 1 断片につき 1 回の LLM 抽出が既定で、LLM なしの経路として GLiNER のデモモデルを持つ ([Cognee cognify](https://docs.cognee.ai/core-concepts/main-operations/cognify))。Mem0 は GPT-4o-mini の function calling で三つ組を作り、Neo4j に入れていた。2026-04-14 の SDK 刷新で、外部グラフストアとグラフ記憶を OSS から削除した。代わりに入ったのは、spaCy の英語モデルで取った実体の共有を、検索の第三の信号として使う仕組みである ([Mem0 migration guide](https://docs.mem0.ai/migration/oss-v2-to-v3))。Letta、LangMem、Microsoft Foundry の記憶は、そもそもグラフを作らない ([codepointer.dev](https://codepointer.dev/p/agent-memory-systems-and-knowledge), [LangMem](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/), [Microsoft Learn](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/what-is-memory))。

| 製品 | LLM なしで張られる辺 | LLM が張る辺 | 抽出の想定モデル | 効果の公開数値 |
|---|---|---|---|---|

| neo4j-graphrag-python | 文書→チャンク、`NEXT_CHUNK`。同一視は完全一致・RapidFuzz・spaCy | エンティティ間の関係、スキーマ推定 | 構造化出力は OpenAI・Vertex・Anthropic のみ | なし |
| LlamaIndex PropertyGraphIndex | パーサ由来の関係 | 三つ組 | 指定なし | なし |
| FalkorDB GraphRAG-SDK | 宣言した表の行と外部キー、文書内の名前の完全一致 | 散文の三つ組、文書をまたぐ同一視 | 評価は gpt-4o-mini | GraphRAG-Bench の自己申告 |
| Memgraph unstructured2graph | GLiNER2 による対象→チャンクの `MENTIONED_IN`、チャンクの `NEXT` | LightRAG 経路の関係と別名の統合 | 既定の GLiNER2 は英語のみ | なし |

表を縦に読むと、製品ごとの違いは「LLM の抽出をどこまで自動化したか」と「どの DB に入れるか」にある。LLM なしで張れる辺の種類は、どの製品でもほぼ同じ 4 種類（文書の構造、埋め込みの近傍、宣言された構造、小型モデルで取った言及）に収まる。Neo4j 自身が運営するパターン集も、チャンクと埋め込みだけの Lexical Graph を最初のパターンに置いている ([graphrag.com](https://graphrag.com/reference/knowledge-graph/lexical-graph/))。**DB は抽出の質を決めない。** 抽出はアプリか SDK の仕事で、DB は保存と探索を担うだけである。400 文書の規模なら、Memgraph や FalkorDB のサーバーを立てて得られる性能上の利点もない（推論）。

## 弱いローカル LLM は精度の前に JSON で落ち、落ちた断片は黙って消える

弱いローカル LLM での失敗は、関係の質が少しずつ落ちるという連続的なものではない。スキーマどおりの構造化出力を返せずに検証で落ち、その断片や episode がグラフから丸ごと消える。LLM Graph Builder の Issue #1123 では、deepseek-r1:1.5b が関係型に文字列ではなく入れ子の dict を返し、pydantic の検証で失敗した。残ったのはチャンクのノードだけだった。メンテナは「LLMGraphTransformer は deepseek のような一部の LLM で、指定したスキーマどおりの構造化出力を得られない。解決策はまだ見つかっていない」と答えている ([Issue #1123](https://github.com/neo4j-labs/llm-graph-builder/issues/1123))。neo4j-graphrag-python の構造化出力は OpenAI・Vertex・Anthropic でしか使えない。しかも既定では、抽出に失敗したチャンクを無視して、成功した分だけを保存する ([User Guide: KG Builder](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_kg_builder.html))。Graphiti の Issue #912 には、Ollama の deepseek-r1:7b だけでなく、70B や llama4 でも必須フィールドが欠けたり、モデルが JSON スキーマそのものを返したりした報告が並ぶ。ホスト型の deepseek-chat でも約 50 件に 1 件が落ちた。MCP のキューはその episode を捨て、辺 0 本のまま HTTP 200 を返していた ([issue #912](https://github.com/getzep/graphiti/issues/912))。

作り手の言葉ははっきりしている。Graphiti の README は、小さいモデルでは誤ったスキーマと取り込みの失敗が「particularly problematic」になると書く ([Graphiti README](https://github.com/getzep/graphiti))。メンテナは「整った JSON を出せる大きなモデルを強く勧める」と答えている ([issue #912](https://github.com/getzep/graphiti/issues/912))。Cognee は、軽いモデルは「noisy or incomplete graphs」を作り、失敗は空のグラフとして現れるとする ([Cognee LLM providers](https://docs.cognee.ai/setup-configuration/llm-providers))。Graphiti には、LLM の抽出なしで episode を追加する選択肢を求める Issue が 2026-03 から出ているが、メンテナの返答はない ([issue #1299](https://github.com/getzep/graphiti/issues/1299))。

モデルの大きさの下限を調べた研究は乏しい。2026-05 の研究は、Microsoft GraphRAG を 8 GB の GPU 1 枚で Ollama 経由で回した。Phi-4-mini（3.8B）は構造化出力の誤りでパイプラインを完了できず、Mistral 7B は退化した繰り返しを出した。著者は、約 7B 未満では有効な構造化出力が安定しないとしている。最大のグラフを作ったのは Llama 3.1 8B だったが、回答が最良だったのは Qwen 2.5 7B で、両者は一致しなかった ([GraphRAG on Consumer Hardware](https://arxiv.org/abs/2605.20815))。モデルを大きくすれば良くなるとも限らない。会話文の三つ組抽出では、Qwen3 を 0.6B から 8B に上げると、precision は 0.818 から 0.953 に上がる一方で、recall は 0.229 から 0.092 に下がり、F1 は 0.358 から 0.168 に落ちた ([LLM-Text2KG'26](https://arxiv.org/html/2607.00003))。なお、GraphRAG-Bench は「7B 前後が実用の下限」という根拠としてよく引かれる。しかしこれは、索引をすべて GPT-4o-mini で作ったうえで、生成側のモデルだけを 3B・7B・14B と変えた結果である（Medical の平均 ACC は 7B で GraphRAG 61.50 対 RAG 56.79）。抽出の下限を示すものではない ([GraphRAG-Bench](https://arxiv.org/html/2506.05690))。以前の調査では、これを抽出側の目安として扱っていたので、ここで訂正する。ローカルの小型モデルで抽出が成り立つ下限の根拠は、上の Consumer Hardware の研究 1 本しかない。

チームが見た「言及 600 件に関係名 597 通り」も、モデルが弱いせいだけではない。KGGen の測定では、Microsoft GraphRAG の既定の抽出器も、100 万文字のコーパスで **辺 981 本に対して関係型 966 通り**を出した。グラフは疎で、重要な関係を落としていた。著者は原因を、実体と関係を統合する段がないことに帰している ([KGGen](https://arxiv.org/html/2502.09956))。neo4j-graphrag-python の 2026 年のリリースも、ノード型や関係型の重複定義を抑える修正と、重複した関係型を自動で調停する修正を繰り返し入れている ([Releases](https://github.com/neo4j/neo4j-graphrag-python/releases))。直すには正規化の段が要り、その段にも強い LLM を使うのが、製品と研究の標準的なやり方である。

日本語では条件がさらに悪い。日本語の文書レベル関係抽出データセット JacRED で、GPT-4 の in-context の関係 F1 は **27.45** だった。教師ありモデルの 68.73 の半分以下である ([JacRED](https://arxiv.org/html/2404.16506v1))。調べた製品はどれも日本語で評価されておらず、既定のモデルは英語向けである。LLM Graph Builder は「英語の長文で最もよく動く」と書いている ([Neo4j Labs](https://neo4j.com/labs/genai-ecosystem/llm-graph-builder/))。neo4j-graphrag-python は、空白のないテキストで分割器が無限ループするバグを 2026 年に直したばかりである ([Releases](https://github.com/neo4j/neo4j-graphrag-python/releases))。Mem0 の実体抽出は `en_core_web_sm` を前提にしている ([Mem0 migration guide](https://docs.mem0.ai/migration/oss-v2-to-v3))。

費用の面でも、ローカルでの抽出は運用にならない。FalkorDB の LLM によるオントロジー検出は、それだけで「文書数 ×（文書あたりの抜き出しチャンク数 + 1）+ 1」回の呼び出しになる ([Ontology Discovery](https://docs.falkordb.com/graphrag/ontology-discovery.md))。400 文書で 1 文書 3 チャンクなら 1,601 回で、チームの実測の 1 回約 52 秒を掛けると、検出だけで約 23 時間かかる（プロンプトの長さの違いを無視した粗い見積もり）。FalkorDB 自身の計測でも、API の gpt-4o-mini を使って 510 チャンクの索引に約 1.5 時間かかった ([Benchmark](https://docs.falkordb.com/graphrag/benchmark.md))。チームの「60 KB に約 2 時間」という実測を 400 本（1 本 3〜5 KB と仮定）に延ばすと、40〜65 時間になる。版が変わるたびに抽出し直す運用は成り立たない。

## 効果は多段と時系列に集中し、文脈の量を揃えると消えかける

効果の独立評価は、2026 年に入って結論の方向がそろった。RAG と GraphRAG を同じ条件で比べた系統評価（arXiv 2502.11371 の v4、2026-11-07）では、Llama-3.1-8B で生成した NQ の F1 は、素の RAG が **64.78**、Microsoft 式のコミュニティ GraphRAG（Local）が 63.01、LLM で抽出した三つ組だけを文脈として渡す KG 型が **34.28** だった。Neo4j の LLM Graph Builder や neo4j-graphrag が作るのは、この KG 型に近いグラフである。チャンクを併せて渡しても 50.27 にとどまる。グラフが勝ったのは、MultiHop-RAG の時系列の質問（RAG 30.70 対 Local 50.60）や比較の質問だった。答えのない質問では、要約を文脈にする Global は「答えがない」と正しく言えた割合が 19.27 にとどまり、RAG の 96.01 を大きく下回った。抽出したグラフに答えの実体が入っていた割合は、HotpotQA で 65.8% だけである。最も重い結果は次の点にある。グラフ側は文脈に 9,770 token、RAG は 3,631 token を使っていた。RAG にも同じ量の token を与えると、RAG は 65.77 から **71.01** に上がり、GraphRAG の **71.17** とほぼ並んだ ([arXiv 2502.11371v4](https://arxiv.org/html/2502.11371v4))。グラフの上積みの多くは、グラフの構造ではなく、LLM に渡す文脈の量から来ていた。ICLR 2026 の GraphRAG-Bench でも、1 問あたりの文脈は素の RAG が 879 token、LightRAG が 100,832 token、MS-GraphRAG の global が 331,375 token で、桁が違う ([GraphRAG-Bench](https://arxiv.org/html/2506.05690))。逆に、抽出器を GPT-4o-mini から GPT-4o に替えると、MultiHop-RAG の値は 75.08 まで上がる ([arXiv 2502.11371v4](https://arxiv.org/html/2502.11371v4))。抽出の質は効く。だからこそ、弱い抽出器でこの上積みは期待できない。

呼び出し側のエージェントが強くなるほど、グラフの価値は縮む。RAGSearch では、GPT-4o-mini で作ったグラフを使っても、RL で学習した検索エージェントを 3B から 7B にすると、密検索との差は平均 14.70 から 9.75 に縮んだ。学習なしのエージェントでも、7B から 32B で 7.80 から 7.19 になった。著者は、一般の QA では密 RAG が実用的だと結論している ([RAGSearch](https://arxiv.org/html/2604.09666v1))。エージェント記憶の自己評価も、グラフの寄与を支えていない。Mem0 は自社の LoCoMo で、グラフ版 Mem0g の上積みを J で **+1.56**（66.88 → 68.44）と報告した。single-hop（67.13 → 65.71）と multi-hop（51.15 → 47.19）ではむしろ下がり、検索の p50 は 0.148 秒から 0.476 秒に延びた。同じ表で全文を渡す full-context は 72.90 で、どの記憶システムよりも高い ([Mem0 paper](https://arxiv.org/html/2504.19413))。その Mem0 は、2026-04 にグラフを OSS から外した。Letta は、gpt-4o-mini のエージェントに会話の履歴をファイルとして置き、検索の道具だけを与えた。その結果は LoCoMo で **74.0%** で、Mem0 のグラフ版の最良値 68.5% を上回った ([Letta blog](https://www.letta.com/blog/benchmarking-ai-agent-memory))。Zep の LongMemEval での上積み（gpt-4o で 60.2 → 71.2）は自社評価である。伸びたのは好み・時系列・セッション横断の集約で、文書に書いてあることを引く性質に近い single-session-assistant は 94.6 から 80.4 に下がった。比較の相手も全文投入で、原文断片のハイブリッド検索ではない ([Zep paper](https://arxiv.org/html/2501.13956))。

ベンダーの数値は、この独立評価を覆す材料にならない。Neo4j の公式資料には、抽出の品質も検索の改善幅も数値がない ([Neo4j blog](https://neo4j.com/blog/developer/knowledge-graph-extraction-challenges/))。Memgraph も評価を公開しておらず、根拠は数値のない顧客事例だけである ([Memgraph docs](https://memgraph.com/docs/ai-ecosystem/graph-rag))。FalkorDB は GraphRAG-Bench での首位（Novel 66.09、Medical 76.87）を主張している。しかしこれは、gpt-4o-mini でグラフを構築し、Cypher を有効にし、埋め込みの次元も変えた自己申告である。競合の値はリーダーボードから写しただけで再実行しておらず、再現の一式も「available on request」で公開されていない ([Benchmark](https://docs.falkordb.com/graphrag/benchmark.md))。Cognee の比較は HotPotQA の 24 問で、自社は調整済み、相手は未調整という条件だったことを自ら認めている ([Cognee benchmarks](https://www.cognee.ai/knowledge-graph-memory-benchmarks))。Mem0 と Zep は、LoCoMo で互いの実装を誤りだと非難し合っている。第三者による再現は見つからなかった ([Zep blog](https://www.getzep.com/blog/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/))。日本語の設計文書のように、中規模・領域固有・日本語のコーパスで GraphRAG と RAG を比べた査読付きの評価は、一本も見つからなかった。日本語で唯一見つかった数値の比較は個人の記事である。単一事実の正解率はベクトル RAG 86・LightRAG 78・GraphRAG 72 で、多段や集約ではグラフが大差で勝った。ただし採点は著者 1 人の主観で、使った LLM も書かれていない ([Qiita](https://qiita.com/kenimo49/items/2ca9ed99889bf9ebe4e2))。方向は上の評価と合うが、差の大きさは信頼できない。

グラフの近傍を文脈として読ませる使い方には、はっきりした害の証拠がある。検索の上位に来たが答えを含まない文書を 1 本足すだけで、Llama2-7B の NQ の精度は 0.5642 から 0.4283 に下がった。こうした文書は、無作為な文書より有害だった ([The Power of Noise](https://arxiv.org/html/2401.14887v4))。答えの文書を 20 文書の中央に置くと、GPT-3.5-Turbo の正答率は 53.8% で、文書を渡さない場合の 56.1% より悪い ([Lost in the Middle](https://arxiv.org/html/2307.03172))。チームが判定した同じ文の共起の辺では、上位 13 組のうち 4 組、無作為な 25 組のうち 3 組しか「深い」と言えなかった。つまり近傍の 7〜9 割は「関連して見えるが答えではない」文書で、これは上の研究で最も害の大きい種類の雑音にあたる。弱いローカル LLM に近傍を広げて読ませる設計は、精度を下げる方向に働く（推論）。

## eumenes_knowledge は LLM なしで作れる層をすでに持ち、その上に積む材料はこの素材に残っていない

eumenes_knowledge の部品を製品の部品に当てはめると、LLM なしで作れる層はほぼ出そろっている。断片への分割と文書との対応は、Neo4j の lexical graph にあたる。FTS（trigram）と multilingual-e5-small の埋め込みは、neo4j-graphrag の HybridRetriever や Cognee の indexing_pipeline にあたる。著者が書いた Markdown のリンクは、LlamaIndex の `ImplicitPathExtractor` や FalkorDB の `TableMapping` と同じ「宣言された構造をそのまま辺にする」経路である。しかも、著者のリンクを辺として取り込む機能は、調べたエージェント記憶の製品のどれにもない。423 文書のうち 349 文書に関連文書を出せるいまの仕組みは、製品群が持たない層をすでに補っている。足りないのは、製品が LLM で作っているエンティティ間の辺と、それを整える正規化と同一視の段だけである。ここまで見たとおり、その層は強い LLM を前提にしていて、効果の証拠も多段・時系列の質問に限られる。製品が LLM なしで張る辺のうち、まだ試していないのは埋め込みの kNN だけである。これは検索と同じ埋め込みの言い換えにすぎない。検索の比較で埋め込みが効くと分かった場合に限り、リンクのない残り 74 文書の関連文書に回せば足りる。

LLM を使わない残りの候補も、この素材で試し終えている。対象とチャンクの型なし二部グラフ（Memgraph の既定と同じ形）を、モデルを使わない名前抽出で作った。すると各文書は、完全一致の名前を介して、ほかの 422 文書のうち平均 420 文書とつながった。5 文書以下にしか出ない名前に限っても平均 78 文書で、コーパスの約 2 割が「隣」になる。これは文書を区別する信号ではなく、チームが共有する語彙を写しただけのものである。同じ文の共起に NPMI で重みを付けても、深い関係は選べなかった。製品で共有名を使う先例は、Mem0 v3 の一つだけである。実体の共有を検索の加点に使い、多くの記憶に出る実体の重みを `1/(1+0.001·(n−1)²)` で弱めている ([codepointer.dev](https://codepointer.dev/p/agent-memory-systems-and-knowledge))。ただしこれは辺ではなく順位付けの補助で、この仕組みだけを外した効果も測られていない。決定的な処理には原理的な限界もある。記憶のパイプラインを 13 構成で比べた 2026 年の研究では、決定的な処理だけでは、言語をまたぐ正規化の成功率が 0% だった ([arXiv 2606.15903](https://arxiv.org/abs/2606.15903))。日英が混ざる設計メモで、モデルを使わない名前の照合が日本語名と英語名をつなぐことはない。

ここに、グラフが置かれた構造的な矛盾がある。グラフの上積みが大きいのは、読み手のモデルが弱いときである（RAGSearch の 3B で差が 14.70）。ところが、そのグラフを作れるのは gpt-4o-mini 級の抽出器だけである。弱いローカル LLM しかない場面ではグラフを作れない。強いコーディングエージェントがいる場面では、エージェントが自分で grep と読み込みを繰り返せるので、グラフの上積みは小さい。Letta のファイル検索の結果は、強いエージェントにとって「生のファイルと検索の道具」がすでに強い基準線であることを示している。強いモデルを API で一度だけ抽出に使う道は残っている。しかし、日本語の文書レベル関係抽出は GPT-4 でも F1 27.45 にとどまり、関係名は強いモデルでも散らばり、効く質問の種類も限られる。この道に投資する根拠が生まれるのは、実際の質問に多段や時系列の問いが多く、しかもそれがハイブリッド検索では取れないと分かったときだけである。

したがって、eumenes_knowledge を「知識グラフ」として十分に意義のあるものにできる見込みは低い。見込みが残るのは、原文の断片を確実に引き、引用を原文と照合して返す「根拠の索引」としての価値で、その上限は控えめである。400 本の Markdown は、強いエージェントなら直接 grep できる量でもある（推論）。ライブラリとしての存在理由は 3 つに絞られる。1 つ目は、埋め込みが言い換えの質問で、FTS や grep の取りこぼしを拾うこと。2 つ目は、自分で検索を繰り返せない弱いローカル LLM に、一度で良い上位 k 件を渡せること。3 つ目は、引用を原文と照合できること。どれもまだ実測されていない。記録にある recall@10 95.3%（FTS だけでは 56.3%）は、台本どおりの fixture と意味を持たない擬似ベクトルで出した値で、実際の文書での性能については何も言っていない。グラフに注いだ工数の大半は、成果物としては回収できない。ただし「この素材では LLM なしのグラフに識別力がない」という否定的な結論は、製品と論文の調査とも一致しており、確定した知見として残る。

## 続けるかどうかは、実際の質問 25 問の検索比較ひとつで決まる

まず、止めるものを挙げる。弱いローカル LLM による抽出は、凍結ではなく廃止にする。関係名の付与と遅延命名も止める。正規化キー・採点・相関クラスタリングによる同一視、共有名や共起による辺、PPR による関連文書、グラフビューアの拡張も止める。どれも「共有ノードが文書をつなぐ」という前提の上に立つ設計で、その前提はこの素材では成り立たなかった。グラフ DB への移行も検討しなくてよい。DB は抽出の問題を解かず、Kùzu は保守が止まっていて、400 文書なら SQLite で足りる。95.3% という数字を設計の根拠として引くこともやめる。残すのは、原文断片のハイブリッド検索、引用の検証、著者のリンクと見出しによる関連文書である。グラフ API は、文書構造とリンクだけの薄いものに保つ。

続けるかどうかは、1〜2 日でできる一つの比較で決められる（所要日数は見積もり）。実際にエージェントや人が過去の知見を引こうとした質問を 20〜30 問集める。共起の辺の検査と同じく、検索結果を見る前に、正解の文書と断片を人が決めて記録しておく（事前登録）。質問には種類の札を付け、次の 4 種類を混ぜる。決定の中身を問うもの、言い換えでしか当たらないもの、英語の識別子で日本語の記述を引くもの、そして「経緯」や「何が何を置き換えたか」を問う時系列のものである。multilingual-e5-small は言語をまたぐ検索で LaBSE に大きく劣る（Tatoeba の平均で 64.2 対 81.1） ([Multilingual E5](https://arxiv.org/html/2402.05672))。英語の識別子で引く問いは、その弱さを確かめるためのものである。測るのは正解文書の recall@10 で、条件は 4 つ置く。FTS だけ、実際の e5 ベクトルだけ、ハイブリッド、ハイブリッドで k を増やしたもの、である。k を増やす条件は、文脈の量を揃えると GraphRAG との差が消えたという結果を、安く再現する対照になる。基準線として、強いコーディングエージェントに生の Markdown のディレクトリと grep だけを与えて同じ質問を解かせ、正解文書に届いたかどうかと、使った token を記録する。弱いローカル LLM については、上位 k 件を渡した場合と渡さない場合で、回答の正否を人が判定する。最初の 10 問で全条件がそろって満点か零点になったら、そこで打ち切って質問を作り直す。e5 は 512 token を超える入力を切り捨てるので ([multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small/raw/main/README.md))、断片の末尾が埋め込みから落ちていないかも同時に確かめる。実際に困った質問を 20 問集められないなら、それ自体が、このライブラリへの需要が弱いことを示す結果になる。

25 問の比較では、数問の差は誤差のうちである。ここでは 5 問以上の差を「明確」とみなす目安を提案する。統計的な根拠は弱いが、決める前に線を引いておくことに意味がある。判断は次の表のとおりにする。

| 比較の結果 | 読み方 | 次の手 |
|---|---|---|
| ハイブリッドが FTS だけより明確に多く当てる | 埋め込みが言い換えを拾っている | 検索の芯（分割、k、再順位付け、引用の検証）に絞って続ける |
| ハイブリッドと FTS がほぼ同じ | 埋め込みが効いていない | 埋め込みを外し、FTS とリンクの薄い索引に縮める |
| 強いエージェントの grep が同等以上 | 強いエージェント向けの価値はない | 弱いローカル LLM での結果だけで継続を決める |
| 弱いローカル LLM が、上位 k 件を渡すと明確に多く正答する | 弱い LLM 向けの存在意義がある | その用途に絞って続ける |
| 外した質問の大半が時系列や経緯の質問 | グラフが効きうる唯一の領域が見えた | API の強いモデルで一度だけ抽出する案を、k を増やした RAG と比べてから検討する |
| どの条件も grep と変わらない | ライブラリとしての意義がない | 開発を止め、grep と著者のリンクで運用する |

続ける価値があるのは、ハイブリッドが FTS と grep を明確に上回るか、弱いローカル LLM の正答が明確に増えるか、のどちらかが成り立つ場合だけである。どちらも成り立たなければ、撤退が正しい判断になる。

## 結論

製品の「知識グラフ」の正体は、強い LLM による抽出サービスとグラフストアの組み合わせである。グラフ DB そのものは知識を生まない。LLM なしで得られる層はどの製品でも同じで、eumenes_knowledge はすでにそこに到達している。行き詰まりの原因は実装の出来ではなく、「強い LLM なしでその先の層を作れる」という前提にあった。その前提を支える製品も研究も、調べた範囲には一つもない。グラフの上積みが最も大きい弱い読み手の場面では、そのグラフを作れないという矛盾も、この方向を内側から閉じている。

問うべきことは「グラフか検索か」から、「この索引は、強いエージェントの grep と弱い LLM の素の回答より良いか」に変わった。徒労感の本当の原因は、グラフの失敗そのものよりも、検索の品質を実データで一度も測らないまま、その上に層を積んできたことにある。チームは深い辺の検査で、事前登録して数十件を人が判定し、結論を出すやり方をすでに身につけている。同じやり方を検索に向ければ、続けるか止めるかは一度の比較で決まる。結果がどちらに出ても、それ以上の作り込みより価値のある情報になる。
